# 01. 参考資料の分析

対象：`reference/JIZURA`（JIZURA 字面 — 文字PV自動構成ツール、MIT License, © 2026 hakoniwa）
目的：JIZURA の機能を Blender Plugin（Extension）として再現できるかを判断する。
除外：**MP4 書き出し**、**After Effects 用書き出し（JSON / AE パネル）** は対象外。

---

## 0. 結論

**再現は可能。** ただし「移植」ではなく **「描画エンジンの置き換え」** になる。

- JIZURA は「歌詞 → カット構成（プラン）を作るロジック」と「プランを Canvas 2D に毎フレーム描く描画エンジン」の2層でできている。
- 前者（パース・分割・タイミング・抽選・おまかせ・音声解析）は**ブラウザ依存がほぼなく、Python にそのまま移せる**。
- 後者は Canvas 2D の即時描画（`fillText` / `clip` / `globalCompositeOperation` / `filter: blur()` / フレーム全体のピクセルコピー）に依存しているため、Blender では **「プランから Blender のシーン（オブジェクト・マテリアル・キーフレーム・コンポジター）を組み立てる」方式** に置き換える必要がある。
- この置き換えは JIZURA 自身の **AE パネルが既に行っている**（プラン → テキストレイヤー・シェイプ・エクスプレッション・エフェクト）。AE で 707 部品すべてを「近い見た目」で組み立てられているので、同等以上の表現力を持つ Blender でも同じ水準は届く。3D の回転・立方体・円筒・旗などは、2D で擬似的に描いているブラウザ版より Blender の方がむしろ得意。
- 難しいのは、**画面全体のピクセルを直接いじる効果**（ピクセルソート・ディザなど）、**要素ごとのぼかし**、**ブラウザ版とまったく同じ見た目・同じ抽選結果**、**大量オブジェクトでのリアルタイムプレビュー**。これらは近似や工夫で対応する（§5）。
- 規模が大きい（部品の描画コードだけで約 2.6 万行の JS）。全部品を一度に移すのではなく、**基本セット（AE 初版と同じ約 80 部品）から段階的に**進めるのが現実的。

### 1.2 処理の流れ

```
歌詞テキスト ─▶ parseLyrics ─▶ 行（強調・!・注釈・/区切り・LRC時刻）
                                  │
曲ファイル ─▶ analyzeAudio ─▶ BPM・拍・音量包絡
                                  ▼
                           computeTiming（行の開始/終了。手動・LRC・文字数×BPM）
                                  ▼
                           plan()：行 → 文節チャンク → カット（1行を1〜数カットに分割、拍にスナップ）
                                   カットごとに部品を重み付き抽選（直近の重複を避ける）
                                   画面効果イベント（色ズレ・揺れ・グリッチ…）を生成
                                  ▼
                           Renderer.frame(t)：時刻 t の1枚を Canvas に描画
```

### 1.3 データモデル

- **project**：歌詞、曲名、スタイル、雰囲気、シード、画面比/解像度/fps、演出スライダー（`motion glitch chroma decor density texture bgSwitch`、フラッシュ、コマ打ち、HUD）、部品ごとの ON/OFF、タイミング設定、行ごとの上書き（鍵・レイアウト指定など）、配色上書き、書体上書き。JSON で保存/読込。
- **plan**：`W H fps duration style fx seed`、`cuts[]`、`events[]`、`beats[]`、`energy[]`。
- **cut**：`text lineText note line start end dur inDur outDur stagger seed emph recap`、部品キー `layout enter hold exit decor[] treat bg cam trans` と各パラメータ（`params treatP bgP camP transP`）、配色番号 `scheme`。
- **event**：`{t, type, amp, dur}`。`type` は `chroma shake slice block invert flash zoom mosaic` と追加の画面効果 58 種。

プランは**純粋なデータ（JSON）**で、描画とは独立している。Blender 側でもこの形をそのまま中間表現にできる。

### 1.4 フレーム描画の順序（`09_render.js`）

1. 時刻を「コマ打ち」で量子化（12枚/秒・8枚/秒・毎フレーム）。ランダムな点滅は 24Hz 基準の `step` で決まる。
2. 背景：配色の地色 + 中央の明るみ（放射グラデ）+ 紙の質感。
3. 背景グラフィック（行ごとに抽選。カメラの影響を受けない）。
4. **本体を3回描く**：色ズレのゴースト B（1.6/24 秒遅れ、ずらし、単色）→ A（0.8/24 秒遅れ）→ main。明るい背景ではゴーストを乗算で重ねる。各パスでカメラ変換 → 後ろの装飾 → レイアウト（歌詞）→ 前の装飾。
5. カメラのぼかしは本体レイヤー全体に1回だけかける。
6. カット間のつなぎ：前カットの最後の画（A）と今の画（B）を合成。
7. HUD（タイムコード・行カウンター）。
8. 仕上げ：画面効果イベント（スライス・ブロック・反転・フラッシュ・ズームブラー・モザイク + 追加58種）→ ブルーム → 走査線 → 粒子 → 周辺減光。

### 1.5 部品システム（10 分類・707 部品）

| 分類 | 数（うち基本） | 単位 | 契約（何を返すか） |
|---|---|---|---|
| レイアウト | 140（17） | カット | 歌詞の配置・大きさ・書体、付随グラフィック。歌詞は必ず `J.mainDraw` を通す |
| 登場 | 100（13） | カット | テキストアイテムを書き換える関数（p=0→1）。文字ごと（`charFns`）・字形部品ごと（`pieceFns`）の変形、クリップ、帯ずらし、残像 |
| 保持 | 38（6） | カット | 静止中の小さな動き（量 0..1） |
| 退場 | 86（11） | カット | p=0→1 で完全に消える変形 |
| 装飾 | 115（15） | カット（0〜3個） | 歌詞の前後に描くグラフィック（枠・線・円・粒子…） |
| 文字の加工 | 52 | カット | 袋文字・立体・影・グラデ・模様・マーカー… |
| 背景 | 62 | 行 | 画面全体の模様（放射・水玉・和柄・星空…） |
| カメラ | 28 | カット | `{x, y, s, rot, sx, sy, skx, blur}` を返す |
| 画面効果 | 66（8） | イベント | 出来上がったフレームのピクセルに対する後処理 |
| カット間のつなぎ | 20 | カット | 前後2枚の画の合成 |

- 各部品は `name / tags（雰囲気）/ w（重み）/ fits（文字数条件）/ plan(rng)→params / render|apply|draw` を持つ。
- **テキストアイテム**は `{text, font, size, x, y, color, align, vertical, track, sx, sy, rot, skew, alpha, stroke, gradient, pattern, shadow, extrude, blur, clip, bands, streak, echo, charFns, pieceFns …}` という豊富なプロパティを持ち、登場/退場/加工はこれを書き換えるだけで成り立っている。**Blender 側ではこのアイテムモデルを「オブジェクト群 + マテリアル + キーフレーム」に翻訳する層が中核になる。**
- 「分解→集合」「爆散」などは、字形をラスタライズして**連結成分（画・部首・点）に分解**し、部品ごとに飛ばしている（`02_fonts.js decompose`）。さらに部品を凸多角形に割る「破片」もある。

### 1.6 スタイル・書体・配色

- スタイル 24 種（基本 12 + 追加 12）。1スタイル = 配色 2〜4 組（`bg fg sub accent accent2 ink dim ghostA ghostB grad paper`）+ 書体の役割（display / serif / body / mono）+ 質感（粒子・紙・走査線）+ 色ズレの強さ + 部品抽選の偏り + HUD 有無 + ブルーム。
- 書体：Google Fonts 18 ファミリーを 23 キー（太さ違い）で使う。必要な書体だけ遅延読み込み。ユーザーのローカルフォント名・.ttf/.otf も使える。
- 配色ランダム：補色ペア表 + 色相環からの生成。背景とのコントラスト比 3 以上に自動補正。

### 1.7 音声解析（`10_audio.js`）

50Hz の音量包絡 → 高域のオンセット強度 → 自己相関で BPM（70〜180、125 付近を優遇）→ 位相探索で拍グリッド。正規化した音量（音圧で伸びる保持などが使う）と波形ピーク（タイムライン表示用）も出す。数十行の数値処理で、外部ライブラリは使っていない。

### 1.8 おまかせ（`08b_omakase.js`）

雰囲気（グリッチ/しっとり/ポップ/グラフィック/エディトリアル/エモーショナル/全部入り）を抽選し、スタイル・演出スライダー・コマ打ち・フラッシュ・HUD・部品の ON/OFF 部分集合・書体・配色・シードを一括で決める。歌詞・タイミング・出力設定・鍵付きの行は変えない。「前の案/次の案」「ここだけ変える（スタイル/配色/雰囲気/構成）」がある。

### 1.9 UI の機能

かんたん/詳細モード、歌詞入力、曲読み込み、タップで同期（Space）、BPM・開始秒・行の長さ・拍スナップ、行リスト（秒数編集・行ごとの再抽選・鍵・部品の直接指定）、タイムライン（波形・カット）、シャッフル、おまかせ、追加分/和風の切替、スタイル・書体役割・フォントファイル・配色、演出スライダー、手法タブ（部品の ON/OFF・絞り込み）、画面比/解像度/fps、背景（通常/グリーンバック/ブラックバック）、プロジェクトの保存/読込。

### 1.10 決定性

描画中に `Math.random()` を使わず、`J.h()`（32bit ハッシュ）と mulberry32 系の乱数列だけを使う。**同じプロジェクト + 同じシードなら同じ結果**になる。Blender 版でも同じ方針をとれば、プランを保存せずにシードから再現できる。

### 1.11 AE 版の移植方針（参考）

AE 版は「プラン → カットごとのプリコンポ（背景・色ズレのゴースト・本体）→ 最上段の調整レイヤーで仕上げ」という構造で、動きは**テキストアニメーターのエクスプレッション**、画面効果は**標準エフェクト**、3D やピクセル加工は**近い見た目に置き換え**ている。ブラウザ版の部品が無い場合は `ae` で指定された基本部品に置き換える仕組み（フォールバック）もある。**Blender 版でもほぼ同じ構造（カット＝コレクション、ゴースト＝時間をずらした複製、仕上げ＝コンポジター）がとれる。**

## 2. Blender での実現方式

### 2.1 方式の比較

| 方式 | 内容 | 長所 | 短所 |
|---|---|---|---|
| **A. シーン生成 + ベイク（推奨）** | プランから、カットごとのコレクション・文字オブジェクト・図形・マテリアルを作り、動きを Python で計算して**キーフレームに焼く**。仕上げはコンポジター、ゴーストは時間をずらした複製 | できた .blend はアドオン無しでも再生・レンダリングでき、手で編集できる（AE 版と同じ価値）。2コマ打ちは「2フレームおきの定数補間キー」で自然に表現できる | オブジェクト数とキー数が多くなる。部品ごとに「Blender の部品での組み立て方」を設計し直す必要がある |
| B. フレームハンドラ駆動 | オブジェクトのプールを用意し、`frame_change_pre` で毎フレーム Python から位置・色・文字を更新 | ブラウザ版のコードを関数単位で写しやすい。キーが不要 | レンダリング時にもアドオンが必須。手で編集できない。Python の処理速度でプレビューが重い |
| C. Python で画像を描いて VSE に並べる | Canvas の代わりに Python の2D描画で連番画像を作る | 見た目を最も忠実に写せる | Blender で作る意味がほぼ無い。Blender 同梱 Python に2D描画ライブラリが無い（Pillow 等を同梱する必要） |

**A を基本とし、毎フレーム文字が変わる部品（スクランブル・タイムコード・カウンター）だけ Geometry Nodes（Scene Time → Value to String / Slice String → String to Curves）で動的にする**のがよい。

### 2.2 JIZURA の概念と Blender の対応

| JIZURA | Blender での対応 |
|---|---|
| デザイン座標（1920×1080 等） | 正投影カメラ。1 デザイン px = 固定の Blender 単位。Z は描画順にのみ使う |
| 配色の hex 色をそのまま出す | カラーマネジメントを **Standard**（AgX/Filmic を使わない）、Emission 主体のフラットシェーダー |
| テキストアイテム | 1文字＝1テキストオブジェクト（文字ごとの変形のため）。縦書き・字間・行送りはアドオン側で配置 |
| `charFns`（文字ごとの変形・透明度・色） | 文字オブジェクトの位置/回転/拡縮 + `object.color`（RGBA）のキー。シェーダーは Object Info の Color/Alpha を読むので、マテリアルを文字ごとに作らずに済む |
| `pieceFns`（字形の部品分解） | 文字をメッシュ化 →「ばらばらのパーツで分離」で連結成分に分ける。ラスタより精度が高い。破片は Bisect で分割 |
| `clip` / `clipY`（ワイプ等の窓） | マスク用 Empty を参照するシェーダー（Texture Coordinate: Object → 比較 → 透明） |
| `bands`（横帯ずらし） | 帯ごとの複製 + 上記クリップ、またはコンポジターの帯変位 |
| `streak` / `echo`（残像） | 透明度を下げた複製 |
| 図形（rect / line / circle / arc / poly / blob / rrect） | カーブ（ベジエ）オブジェクト + ベベル（線幅）/ フィル。線の描き順アニメ（`polyPartial`）は **Bevel Start/End Factor** のキーでそのまま表現できる |
| 文字の加工（袋文字・立体・グラデ・模様など） | テキストの Offset/Extrude/Bevel、Geometry Nodes でのアウトライン、シェーダー（グラデ・水玉・斜線・ストライプ）、複製 |
| 背景グラフィック | 画面いっぱいの平面 + プロシージャルシェーダー（Noise / Voronoi / Wave / Gradient / 数式ノード）。和柄など複雑な模様はタイル画像を Python で生成して貼る |
| カメラ | 正投影カメラ（またはカット用の親 Empty）の変形キー。ぼかしはコンポジター |
| 色ズレの3パス | カット内容の複製2組（キーを 0.8/24・1.6/24 秒ずらす、ゴースト色の単色マテリアル）。明るい地の乗算は Transparent BSDF の色（＝乗算）か、ビューレイヤー分け + コンポジターの Mix（Multiply）で行う |
| 画面効果イベント | コンポジターのノード（Glare・Lens Distortion・Pixelate・Directional Blur・Displace・Invert・Mix・Posterize・Filter など）のパラメータをキーで動かす |
| カット間のつなぎ | 前カットを最終状態で止めたまま残し、マスク（形をキーで動かす平面・ホールドアウト）や 3D の回転で合成。画像ベースのつなぎは VSE のシーンストリップ + Wipe（Single/Double/Iris/Clock）も使える |
| 粒子・紙・走査線・周辺減光・ブルーム | コンポジター（Glare の Bloom、Ellipse Mask、生成画像との Mix） |
| 曲 | VSE のサウンドストリップ。解析は `aud.Sound(path).data()`（numpy 配列）で読み、numpy で JIZURA と同じ計算をする |
| タップで同期 | 再生中にキーを押すと現在フレームを記録するモーダルオペレーター、または**タイムラインマーカー（M キー）を行頭として読む**（AE 版の「マーカーを行頭に使う」と同じ） |
| 歌詞入力 | Blender の Text データブロック（テキストエディタ）を歌詞欄として使う。パネルには行リスト（UIList） |
| プロジェクト設定 | シーンに持たせる PropertyGroup（.blend に保存される）。JSON 読み書きも可 |
| フォント | `bpy.data.fonts.load()` で .ttf/.otf を読む。Google Fonts は OFL なので同梱できる。字幅は fontTools（Extension に wheel 同梱可）で hmtx/vmtx を読む |
| 文節分割（`Intl.Segmenter`） | Python 標準には無い。JIZURA 内蔵の文字種ベースの分割（フォールバック実装）を移植、必要なら BudouX（純 Python・小さい）を同梱 |

## 3. 再現が可能な内容の一覧

難易度：**低**＝ほぼそのまま移せる／**中**＝Blender の機能での組み立て直しが必要／**高**＝工夫が要るが実現できる見込み

### 3.1 プラン生成・ロジック

| 機能 | Blender での実現 | 難易度 |
|---|---|---|
| 歌詞の記法（`/` 区切り・`*強調*`・行末 `!`・`|注釈`・LRC 時刻・`#` コメント・`[ti:]` 等） | Python に移植 | 低 |
| 文節チャンク分割・長いチャンクの分割・1文字かなの結合 | 文字種ベースの分割を移植（BudouX で改善可） | 低 |
| タイミング計算（文字数・BPM・行の長さ倍率・空行の間・手動秒数・LRC・曲の長さ） | Python に移植 | 低 |
| カット分割（カットの細かさ・まとめ直し・拍スナップ） | Python に移植 | 低 |
| 部品の重み付き抽選（スタイルの偏り・直近の重複回避・縦画面補正・強調補正・文字数条件） | Python に移植 | 低 |
| 画面効果イベントの生成（24fps 基準） | Python に移植 | 低 |
| 間奏カット・タイトルカード | Python に移植 | 低 |
| 決定的ハッシュ・乱数・イージング・ノイズ | Python に移植（32bit 演算を合わせる） | 低 |
| おまかせ（7 雰囲気）・前の案/次の案・ここだけ変える | Python に移植 + 履歴をシーンに保存 | 低 |

## 4. 再現が難しい内容の一覧

| # | 内容 | 難しい理由 | 対応方針 |
|---|---|---|---|
| 1 | **ブラウザ版と同じ見た目（ピクセル単位）** | 文字のラスタライズ・アンチエイリアス・合成モード・ぼかしの実装がまったく違う | 「同じ構成・同じ動きで、近い見た目」を目標にする（AE 版と同じ割り切り） |
| 2 | **ブラウザ版と同じシードで同じプラン** | 文節分割に `Intl.Segmenter`（ICU 辞書）を使っており Python では同じ結果が出ない。浮動小数・ハッシュの細部も一致させる必要がある | Blender 内で「同じシード→同じ結果」を保証すれば十分とする。完全一致が必要なら、ブラウザ版からプラン JSON を受け取る読込口を別途作る |
| 3 | **画面全体のピクセル演算に依存する効果**：ピクセルソート・1bit ディザ・網点（画面全体）・万華鏡・ピクセルずれ・ブロックノイズ | コンポジターに「並べ替え」「誤差拡散」などのノードが無い | 近似（Directional Blur + しきい値マスク、生成パターン画像との比較、Map UV + 生成した UV 画像）。AE 版も同じく近似 |
| 4 | **要素ごとの任意のぼかし**（ブラー登場/退場・ぼかし影・発光・ぼかし送り） | EEVEE にはオブジェクト単位のぼかしが無い。ぼかしはコンポジターでビューレイヤー単位になる | 「ぼかし用ビューレイヤー」に移してコンポジターでぼかす（同時に違う量のぼかしが要る場合は近似）、半透明の複製を重ねる、被写界深度を使う（正投影での EEVEE の DoF 挙動は要検証） |
| 5 | **オブジェクト単位の合成モード**（差の絶対値・スクリーン・オーバーレイ） | EEVEE のマテリアルは通常合成か、Transparent BSDF による乗算までしかできない | 必要な部品だけビューレイヤーを分けてコンポジターの Mix で合成 |
| 6 | **文字を画像として標本化するレイアウト**（ドットマトリクス・モザイク文字・網点巨大文字など、`getImageData` を使う 3 箇所） | Canvas でラスタライズして画素を読んでいる | 文字をメッシュ化し、格子点が字形の内側か判定（BVH / Geometry Nodes のレイキャスト）。中〜高 |
| 7 | **画像ベースのつなぎ**（タイル崩落・ブロック崩し・モザイク転換） | 「前カットの最後の画」を画像として切り刻む必要がある | 前カットを別ビューレイヤーで描きコンポジターでマスク合成、または前カットの最終フレームを先にレンダリングして画像として平面に貼る（2段階レンダリング） |
| 8 | **リアルタイムプレビューの速さ** | ブラウザは毎フレーム即時描画で軽い。Blender では1曲（100〜200 カット）で文字・図形・ゴーストの複製を含め数千〜数万オブジェクトになり、コンポジターも重い | カットの時間外は非表示（`hide_viewport/hide_render` のキー）、ゴーストはプレビュー中オフ、プレビュー解像度を下げる、範囲を区切って生成する、必要なら Geometry Nodes のインスタンスでまとめる。最初の試作で実測が必要 |
| 9 | **Google Fonts の必要な分だけ遅延読み込み** | Blender にはブラウザのような Web フォント機構が無い。日本語フォントは1書体 数 MB〜十数 MB で、18 ファミリー・太さ違いを同梱すると大きい | 同梱する書体を絞る、初回にダウンロード（Extension の network 権限が必要）、ユーザー指定フォントで代用。可変フォントの軸は Blender で使えないので、太さごとの静的フォントを用意する |
| 10 | **画面上の UI 体験**（かんたんモード・行リストでの直接編集・タップで Space） | Blender のパネルには複数行の入力欄が無い。Space は再生/停止に割り当て済み | 歌詞はテキストエディタで入力、タップはマーカー（M）か別キーで記録。かんたんモードは「おまかせ・前/次の案・ここだけ変える」だけのパネルで代替 |
| 11 | **707 部品すべての移植量** | 部品の描画コードは JS で約 2.6 万行あり、1部品ずつ Blender 向けに組み立て方を設計し直す必要がある | 基本セットから段階的に移す。未移植の部品は AE 版と同じく「最も近い基本部品」に置き換える仕組みを最初から入れる |
| 12 | **Canvas のフィルター文字列やパターン塗り** | `ctx.filter`・`createPattern` 等の描画 API は Blender に無い | シェーダー・コンポジターで個別に置き換え（上の一覧に含まれる） |

## 5. 要検証事項（試作で確かめること）

1. 1曲分（100〜200 カット）を生成したときのオブジェクト数・生成時間・ビューポート再生の fps・レンダリング時間。
2. 文字ごとのオブジェクト方式と Geometry Nodes（String to Curves のインスタンス）方式の速度比較。
3. 正投影カメラでの EEVEE の被写界深度（要素ごとのぼかしに使えるか）。
4. ビューポートのリアルタイムコンポジターで、使いたいノードがすべて動くか。
5. 日本語フォントのメッシュ化・連結成分分離の品質（輪郭が重なっているフォントで余分に割れないか）。
6. `aud.Sound.data()` で MP3 / WAV / M4A を読めるか、長い曲でのメモリ。
7. 対象 Blender バージョンの決定（Extension 形式は 4.2 以降。EEVEE Next の仕様差、Geometry Nodes のノード有無が変わる）。

## 6. 対象外とするもの

- MP4 書き出し（WebCodecs / mp4-muxer）
- After Effects 用書き出し（AE 用 JSON、`JIZURA_AE.jsx`、`ae/` 一式）
- 連番 PNG / 透過 PNG の ZIP 書き出し（Blender の標準レンダリングで代替できるため、書き出し機能としては作らない）
- ブラウザ固有の機能（GitHub Pages での公開、ブラウザ内処理であることの説明表示など）
